\subsection{Unit}

The shared package checks the rules a contest uses. A penalty counts only the rejections before the first accepted answer. A quiz answer scores full marks at the start and half marks at the deadline. A rating moves toward the contest result and never falls below 100. \texttt{publish}, and any tool name we do not recognise, is denied.

The agent checks that a mutant is a small edit of the reference, that a model reply which is not the allowed JSON is dropped, and that the pipeline still scores a suite when no model is configured.

Mail is five checks on the address, not a live send. Mailpit stays on port 1025 with no password. A relay on port 587 turns on STARTTLS and decodes a password that contains \texttt{@}. \texttt{smtps} is port 465. Port 25 is refused, because Oracle Cloud blocks it. The local-inbox link is returned only when the host is this PC. A real relay returns no local link, so the page tells the person to open their own email. On 6~November the public host used that relay: one register to our Gmail address returned \texttt{mailed: true}, with no code and no inbox link in the response.

\subsection{Integration}

\path{server/src/http/flows.test.ts} walks a problem from a draft, through the publish check, into the archive. It seats one user, waitlists the next, and promotes the first waiter when someone withdraws. It runs a contest, freezes the board, ends it, and publishes ratings. It also refuses a seat until the email is verified.

\path{auth.test.ts} checks the security routes. A participant receives 403 on an admin route, and the denial is written to the audit log. A used refresh token cannot mint a new session. An admin can change a role. A person can rename the account.

\path{domain.test.ts} is the concurrency file, described in \S\ref{sec:conc}. After the six-digit code, these three files were run again: 49 tests, pass. A signup against Mailpit returned \texttt{mailed: true}, and the code in that inbox verified with HTTP 200.

\section{Concurrency}
\label{sec:conc}

\path{server/src/domain/domain.test.ts} registers 400 distinct users into a contest of 200 seats. The coverage run recorded that case at about 87 seconds. The result is exactly 200 seats and no duplicate seat.

The write is one filtered update. A seat is inserted only while \texttt{reserved < capacity}, and a unique partial index rejects a second active seat for the same user. Two requests cannot both observe spare capacity and both commit. The same file checks that a stale judge claim token does not apply a second verdict, and that a first solve is awarded once.

Our demo contest Last seat has capacity 1 and registration open. Two browsers register. One is seated and one is waitlisted. That is the same filter, with a room of one.

\section{Deployment}
\label{sec:deploy}

This section says what has to be running for CodeClash to work, what is running at \url{http://129.225.92.29}, and why that machine spends trial credit instead of sitting on Always Free.

\subsection{What a running CodeClash is}

A person opens the site in a browser. That page is not the whole system. Behind it, six other programs have to be alive at the same time.

\begin{enumerate}
\item The \textbf{page} is the React app. In development it is served by Vite at \url{http://127.0.0.1:5173}. On a server it would be ordinary files, served by Caddy.
\item The \textbf{server} answers the page. It is a Node program on port 4000. Sign-in, contests, submissions, and the live scoreboard all go through it. The live scoreboard is a Socket.IO connection that stays open. A host that only serves files cannot hold that connection.
\item \textbf{MongoDB} stores the users, the contests, the problems, and the verdicts. We run it as a replica set named \texttt{rs0} because a few of our writes need a transaction. It listens only on this machine.
\item \textbf{Redis} is the queue, not the database. When someone submits, the server does not run the code. It appends a message to a Redis stream. There are three streams: \texttt{judge:contest}, \texttt{judge:practice}, and \texttt{agent:harden}.
\item The \textbf{judge} is a second Node program. It takes one message off the stream and starts a throwaway Docker container. That container is the sandbox: no network, almost no permissions, a time limit, and then it is deleted. The judge needs the Docker socket of the same machine. It cannot live on a host that is not allowed to start containers.
\item The \textbf{agent} is a third Node program. It takes a message off \texttt{agent:harden} when a setter presses Check. It is the bot in \S\ref{sec:bot}. It can run without a Gemini key. With a key, it also asks the model for attacks.
\item \textbf{Mail} on this laptop is Mailpit. Signup sends a six-digit code, the page says the code is in the local inbox, and it links \url{http://127.0.0.1:8025}. SMTP is port 1025. On the public host the same page uses Oracle Email Delivery on port 587. A real relay returns no local link, so the page tells the person to open their own email.
\end{enumerate}

So ``deploy'' here means one computer that runs all of these together. It does not mean uploading the React app to a static host. A static host cannot start a container for each submission, and it cannot keep the scoreboard socket open.

\subsection{The public host}

The address other people can open is \url{http://129.225.92.29}. It is one Ubuntu 24.04 machine in India South (Hyderabad), shape \texttt{VM.Standard.E5.Flex}, 1~OCPU and 8~GB. We started it on 6~November 2026. It is not Always Free. It spends the \$300 trial credit. We delete it on 20~November 2026. If it is still running when the 30-day trial ends, the card is charged.

\begin{enumerate}
\item Docker runs MongoDB, Redis, and Mailpit. Each published port is bound to \texttt{127.0.0.1}. Caddy does not forward the inbox, and the API port stays closed to the internet.
\item Caddy on port 80 serves the built page and forwards \texttt{/api}, \texttt{/socket.io}, \texttt{/health}, and \texttt{/metrics} to the server on port 4000.
\item Three systemd units start the server, the judge, and the agent. The judge uses that machine's Docker. We pulled the six language images before the first submit.
\item The Ubuntu image allowed only SSH. We opened ports 80 and 443 and saved the rules, so a reboot keeps the site up.
\item Signup uses Oracle Email Delivery on port 587. The approved sender is the Gmail address we registered with Oracle. A register of that address returned \texttt{mailed: true}, with no code in the JSON and no local-inbox link. The server log has no send error, so the relay accepted the message. We have not opened that Gmail inbox. Gmail can still drop a \texttt{gmail.com} From address that Oracle signed.
\end{enumerate}

We signed in on that page, opened ``One number of FizzBuzz'', and submitted Python. The page said Accepted. The first click did not. The site is plain HTTP, and \texttt{crypto.randomUUID} exists only on HTTPS and on localhost, so the button reported \texttt{crypto.randomUUID is not a function} and queued nothing. \texttt{newIdempotencyKey} falls back to \texttt{getRandomValues} on that page. After we rebuilt the client, the same submit was Accepted.

The two hardening files we open in the slot are already saved, so we do not wait for a new model call: \path{Deliverables/demo/hardening.json} and \path{Deliverables/demo/hardening-empty.json}.

\subsection{Why this is not an Always Free machine}

Oracle's Always Free Ampere shape, \texttt{VM.Standard.A1.Flex}, is the one that can hold this stack. The limits call on 6~November said the quota was unused. Every launch in Hyderabad still returned ``Out of host capacity'': 2~OCPU and 12~GB, 1~OCPU and 6~GB, each fault domain, and no fault domain. Quota is not a free host. \texttt{VM.Standard.E4.Flex} at 1~OCPU and 8~GB was out of capacity as well. The E5 shape at that size started.

A 1~GB machine does not fit the judge we ship. The compile container asks for 512~MB and turns swap off, and the Java floor is 512~MB, beside the operating system, Docker, and Mongo. The Always Free AMD micro is that 1~GB size. We did not shrink the judge to make it fit. Google's always-free \texttt{e2-micro} and Azure's free B-series are 1~GB too, and a static host cannot start a container per submission. Our AWS account still lists only Glue, so an EC2 instance would have billed the card directly. The trial credit is what carries the demo until 20~November. The steps and the delete date are in \path{deploy/README.md}.

\subsection{Shared stages}

Both pipelines run these stages. The model steps are the only ones that disappear when the key is absent.

\begin{enumerate}
\item Baseline. The reference runs on the tests we already stored. If it fails one, the note says so and we do not trust the score.
\item Mutants. Deterministic edits of the reference: a relational operator, an off-by-one, a dropped element.
\item Replay. Each mutant runs on the stored tests. One that fails a sample is trivial. One that fails a hidden test is killed. One that still matches is survived.
\item Attacks from the spec: boundary, about 25 random inputs, and one max-scale input. With no spec we derive a few inputs from the shape of the samples, and we skip boundary and max-scale.
\item Model plan, only when a planner is attached. At most one call. The reply may contain a wrong program, an edge-case input, or a slow program. A \texttt{tool} field the gate denies is dropped and audited.
\item The reference runs every new input. A crash, an empty answer, or an answer over 64~KB is dropped.
\item Survivors face every accepted attack.
\item Model feedback, only when a planner is attached and something still survived. One more call. That is the second and last call of the run.
\item A deterministic mutant that survived the suite and at least 25 random inputs is marked equivalent. We do not propose a test for it.
\item Proposals. The shortest input that kills a survivor. A wrong program the current tests already catch is held, not added again. If the largest stored test is under half the maximum input size, we also propose the max-scale input.
\item Score. Killed deterministic mutants divided by those that are killed or still survived. Equivalent edits and compile errors are out of the denominator. The score is null when nothing is eligible.
\end{enumerate}

\subsubsection{Larger of two}

The problem is: read two integers and print the larger one. If they are equal, print that value. The reference is one comparison, \texttt{a >= b}.

We started with the sample only. The input is \texttt{3 1} and the output is \texttt{3}. The first number is already the answer, so a program can ignore the second number and still pass.

Two programs the model wrote survived that sample.

\begin{lstlisting}
print(a if abs(a) >= abs(b) else b)
\end{lstlisting}

On \texttt{3 1} the absolute values are 3 and 1, so it prints 3, which matches. It is wrong as soon as both numbers are negative, because it compares sizes and then prints the original number it thinks is larger.

\begin{lstlisting}
ans = 0
if a > ans: ans = a
if b > ans: ans = b
print(ans)
\end{lstlisting}

On \texttt{3 1} both numbers are above 0, so it prints 3. If both numbers are negative it never moves off 0, and it prints 0.

The run asked for \texttt{-100 -50}, with expected output \texttt{-50}.

\subsubsection{Balanced brackets}

The problem is a string of parentheses. Print \texttt{yes} if they are properly nested, and \texttt{no} otherwise. The reference walks the string with a depth counter. \texttt{(} adds one, \texttt{)} subtracts one. The string is balanced only when the depth never goes negative and ends at zero.

\begin{lstlisting}
print("yes" if ok and d == 0 else "no")
\end{lstlisting}

The sample is \texttt{(())}, and the answer is \texttt{yes}. Depth goes 1, 2, 1, 0. It never goes negative, and it ends at 0, so both halves of the condition are true.

The edit that survived flips \texttt{and} to \texttt{or}.

\begin{lstlisting}
print("yes" if ok or d == 0 else "no")
\end{lstlisting}

On \texttt{(())} both halves are still true, so \texttt{or} also prints \texttt{yes}. The sample cannot see the bug. The score was 0, and the projected score after the proposed test was 1.

The shortest input the run asked for is a single \texttt{(}, expected \texttt{no}. Depth ends at 1, and it never went negative, so \texttt{ok} is true and \texttt{d == 0} is false. \texttt{and} prints \texttt{no}. \texttt{or} prints \texttt{yes}.

We saved that line. We also added two neighbours a setter would write once the sample is only the happy path:

\begin{itemize}
\item \texttt{)(} $\to$ \texttt{no}. One open and one close, so a program that only counts them says \texttt{yes}. The close comes first, so the depth goes negative.
\item \texttt{(()} $\to$ \texttt{no}. Two opens and one close. The string ends still open.
\end{itemize}

The next run killed the \texttt{and}/\texttt{or} edit. The score was 1. A different program still survived. It does not track depth at all. It says \texttt{yes} when four cheap checks pass: the length is even, the string starts with \texttt{(}, it ends with \texttt{)}, and the two counts are equal.

\begin{lstlisting}
if (len(s) % 2 == 0 and s.startswith("(")
    and s.endswith(")") and s.count("(") == s.count(")")):
    print("yes")
\end{lstlisting}

\texttt{)(} kills a pure counter, because that program does not require the string to start with \texttt{(}. This one does, so \texttt{)(} is not enough. The run asked for \texttt{())(()}, expected \texttt{no}. Length 6, starts with \texttt{(}, ends with \texttt{)}, three opens and three closes, so the cheap checks all pass and the program prints \texttt{yes}. The depth goes 1, then 0, then $-1$. The reference prints \texttt{no}. We saved that string. The following run killed the program.

What the run still asked for, and what we did not add, is a long string. One model program is correct and slow: it deletes \texttt{()} until the string is empty, which is quadratic. It matches the reference on every short test. Timing it out needs a string of about 64{,}000 characters. That is a time-limit test, not a wrong answer. The correctness cases are done.
